如何部署一个类似此网页的个人网站

2025-03-26

  • 部署
  • Hugo

搭建这个博客，核心是三件事：把文章写成 Markdown，让 Hugo 生成网页，再把网页交给托管服务。 平时写作不需要维护数据库，也不需要在服务器上一直运行 Hugo。

本文使用 Hugo + Bear Blog 主题 + GitHub + Netlify，先在本地跑通，再配置自动发布。本站在 Bear Blog 基础上修改了布局、配色、代码块与交互演示，直接安装主题会得到它的基础样式。

本文于 2026 年 11 月重新整理。旧版中不完整的主题安装过程、失效的嵌套链接和依赖旧界面的截图，已改为可以对照执行的步骤。示例配置以本次本地验证的 Hugo 0.169.0 为基准；以后使用其他版本时，让本地和构建环境保持一致。

1. 先理解文件是怎样变成网站的

Markdown 文章 + Hugo 模板 + 图片、CSS、JavaScript
                       ↓ hugo
                 public/ 静态网页
                       ↓ 托管服务
                 访客浏览器打开网站

Hugo 只在构建时运行。hugo server 用于本地预览；正式发布时运行 hugo，再发布生成的 public/。两者的用途不同，不要把开发服务器当成正式部署方式。

静态网站也可以有交互。本站的像素草地拆解就是文章、JavaScript 和 WebGL 的组合：服务器提供文件，访客浏览器负责运行演示。

2. 安装工具，确认终端能找到它们

需要安装 Hugo、Git，以及用于登录和创建远端仓库的 GitHub CLI。安装方式见 Hugo 安装文档、Git 下载页和 GitHub CLI。

安装完成后打开一个新终端，分别执行：

hugo version
git --version
gh --version

三个命令都应输出版本。如果出现“command not found”或“不是内部或外部命令”，先检查可执行文件所在目录是否加入 PATH，并重新打开终端。Windows 手动解压 Hugo 时，加入 PATH 的是包含 hugo.exe 的目录。

不同主题对 Hugo 版本和 Sass 工具有不同要求，应先看主题文档；不要把“安装某个版本”当成能解决所有主题报错的办法。本教程使用的基础 Bear Blog 主题不需要先安装一套 Node.js 构建工具。

3. 创建博客，添加主题

下面的命令用于创建一个新博客。如果你已经有自己的仓库，就在现有仓库中继续，不要再次执行新建命令覆盖文件。

hugo new site my-blog
cd my-blog
git init -b main

my-blog 是本地目录名，可以自己修改。新版 Hugo 也可以使用 hugo new project my-blog；site 是兼容别名。

先确认 GitHub 登录状态。如果还没登录，执行 gh auth login，按终端提示通过浏览器完成授权。

gh auth status

将 Hugo Bear Blog添加为 Git 子模块：

git submodule add https://github.com/janraasch/hugo-bearblog.git themes/hugo-bearblog

以后在另一台电脑拉取这个新仓库时，需要同时取得主题：

git submodule update --init --recursive

Hugo 会自动读取主题的模板，不需要把主题的整个 layouts/ 复制到项目根目录。需要定制哪一个模板，再复制并修改对应文件，能避免不必要的模板覆盖。

4. 配置站点并写第一篇文章

在新项目的 hugo.toml 中设置最基本的信息。example.org 是占位域名，获得实际地址后需要替换。

baseURL = "https://example.org/"
title = "我的个人博客"
languageCode = "zh-CN"
theme = "hugo-bearblog"
enableRobotsTXT = true

[params]
  description = "记录学习、项目和日常观察。"

[permalinks]
  blog = "/:slug/"

[markup.highlight]
  noClasses = true

这里保留 languageCode 是为了与本教程使用的 Bear Blog 模板一致。Hugo 0.169.0 会提示它已弃用，但仍可以构建；升级到移除该字段的版本前，需要一起迁移配置和引用 .Site.LanguageCode 的模板。

noClasses = true 会让 Hugo 在高亮标记中直接携带颜色，适合先确认代码块能正常显示。像本站这样需要随明暗主题切换颜色时，可以改用 noClasses = false，并加载对应的 Chroma CSS；只改配置而不加载样式，代码仍然会是单色。

创建 content/_index.md，写上首页介绍：

+++
title = "你好，我是……"
+++

这里记录我的项目、学习笔记和一些有趣的实验。

然后创建首篇文章：

hugo new content blog/hello-world.md

将生成文件的内容调整为：

+++
title = "我的第一篇博客"
date = "2026-11-08T12:00:00+08:00"
slug = "hello-world"
draft = false
+++

## 为什么开始写博客

把做过的事情整理下来，也给以后的自己留一份参考。

日期改成自己的写作日期。slug 决定文章地址，这里是 /hello-world/；以后修改标题时，保留 slug 可以避免链接跟着变化。draft = true 的内容默认不会进入正式构建。

5. 本地预览，再检查正式构建

在包含 hugo.toml 的项目根目录运行：

hugo server --bind 127.0.0.1 --port 1313 --renderToMemory

打开终端显示的本地地址，通常是 http://127.0.0.1:1313/。保持终端运行，修改 Markdown 后页面会自动刷新；按 Ctrl+C 停止。--renderToMemory 让预览输出保存在内存中，避免把带有 localhost 链接的预览文件写进 public/。

需要预览草稿时，追加 -D；准备发布时仍应确认文章已设为 draft = false。更多参数见 Hugo 基本用法。

再执行一次正式构建：

hugo --minify

构建成功后，确认 public/index.html 和文章目录存在。依次检查首页、文章、图片、代码块，以及手机宽度下的布局。终端中的 ERROR 需要先处理；WARN 也应读清具体原因，尤其是版本弃用提示。

6. 把源码保存到 GitHub

对于本教程的“Netlify 从源码构建”流程，在项目根目录创建 .gitignore：

/public/
/resources/_gen/
.hugo_build.lock
.DS_Store

public/ 是构建结果，可以重新生成；应维护的内容是文章、配置、模板、主题引用和静态资源。如果旧仓库已经跟踪 public/，新增忽略规则不会自动取消跟踪，不要直接套用到不同的发布流程。Hugo 的 Netlify 部署文档也采用发布时重新构建的方式。

确认暂存内容后提交：

git add .
git diff --cached --stat
git commit -m "建立个人博客"

通过 GitHub CLI 创建仓库并推送：

gh repo create my-blog --private --source=. --remote=origin --push

这条命令用于还没有远端的新项目。已有 origin 时直接使用现有仓库，不要再次创建。

源码仓库可以保持私有；后续需要授权 Netlify 读取它。公开网站与公开源码是两件事，不必为了让别人访问博客就把所有源码公开。

7. 让 Netlify 自动构建和发布

本节采用Netlify 直接读取 Hugo 源码仓库的方案。在根目录新增 netlify.toml：

[build]
  command = "hugo --minify"
  publish = "public"

[build.environment]
  HUGO_VERSION = "0.169.0"
  TZ = "Asia/Shanghai"

把 HUGO_VERSION 改为你已经在本地验证通过的版本，再提交这个文件：

git add netlify.toml
git commit -m "配置 Netlify 自动构建"
git push

在 Netlify 中选择导入现有项目，连接 GitHub，并授权读取刚创建的源码仓库。核对以下内容后启动部署：

设置 本教程的值
生产分支 main
基础目录 项目位于仓库根目录时留空
构建命令 hugo --minify
发布目录 public
Hugo 版本 与本地验证版本一致

关键是让 Netlify 执行 Hugo，再发布 public/，而不是把 Markdown 源码直接作为网站目录。Netlify 对 Hugo 的框架识别、版本选择和主题处理见官方说明。

首次部署完成后，Netlify 会给出站点地址。将它写入 hugo.toml 的 baseURL，使用完整的 HTTPS 地址和结尾斜杠，再提交、推送一次。后续推送到生产分支会触发重新构建。

8. 使用自己的域名

先用 Netlify 提供的地址确认站点正常，再在项目的域名设置中添加自己的域名。根据控制台给出的记录配置 DNS，等待解析和 HTTPS 证书就绪。不要照抄别人的 IP 或 DNS 记录，不同配置方式需要的值可能不同。

域名可用后，将 baseURL 改为最终地址。例如本站的公开地址是：

baseURL = "https://huyuqwqovo.top/"

这是本站的域名示例，搭建自己的站点时请替换。提交配置后检查文章链接、RSS、sitemap 和分享图片是否都使用新域名；仅让首页能打开，还不足以说明所有链接都正确。

9. 本站现有流程与新站教程有什么区别

本文前面介绍的是单仓库流程。本站现有 .github/workflows/deploy.yml 则采用了另一种结构：源码推送到 main 后，GitHub Actions 执行 Hugo，再将文件推送到 zzz-k-k/my_blog 发布仓库。

工作流中的步骤名虽然写着 “Deploy to GitHub Pages”，实际使用的 Action 也可以把文件推送到其他仓库。步骤名称不能证明网站由 GitHub Pages 托管。 本站线上响应中能看到 Netlify 和 Cloudflare 标识。

维护这种结构时，需要分别确认两段是否成功：

  1. GitHub Actions 是否完成构建，并把本次提交对应的内容写入发布仓库。
  2. 托管端是否已经更新到新的产物，公开域名是否显示新页面。

新建博客通常不必复刻这层发布仓库。如果已经在维护旧站，则要先看实际工作流和托管配置，再决定是否调整；不要混用“源码仓库构建”与“直接发布现成产物”两套设置。

10. 日常更新与常见问题

以后写作的基本节奏是：编辑 content/blog/ 中的 Markdown → 本地预览 → 正式构建检查 → 提交并推送 → 查看部署结果。

现象 先检查什么
本地找不到主题 theme 是否与目录名相同；主题子模块是否已初始化
本地正常，远端构建失败 远端 Hugo 版本、主题是否存在，以及构建日志中的第一处实际错误
新文章不出现 draft 是否为 true；日期是否在未来；是否推送了正确分支
首页正常，文章或图片 404 baseURL、文章 slug、资源路径与文件名大小写
正式页面出现 localhost 是否误发布了开发预览产物；正式发布前重新运行 Hugo
代码没有颜色 是否使用类名高亮却没加载 Chroma 样式；代码围栏是否注明语言
改了文章但线上没更新 提交是否已推送、构建是否成功、访问的是否是生产域名

最后记住这些目录的分工：

my-blog/
├── content/              # 文章与页面
├── layouts/              # 自定义模板和 shortcode
├── static/               # 原样发布的图片、CSS、JavaScript
├── themes/               # 主题
├── archetypes/           # 新文章的初始模板
├── hugo.toml             # Hugo 配置
├── netlify.toml          # 本教程使用的托管构建配置
└── public/               # 生成结果，不在这里编辑文章
